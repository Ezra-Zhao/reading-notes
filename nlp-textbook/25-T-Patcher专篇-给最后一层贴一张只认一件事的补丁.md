# NLP 读书笔记（25）：T-Patcher 专篇——给最后一层贴一张只认一件事的补丁

> 来源：中文 NLP 教材（浙江大学），《Foundations of LLMs》讲义第五章 5.3 节
> 覆盖：书页码 205–210（5.3.1 补丁的位置；5.3.2 补丁的形式，式 5.6–5.7；5.3.3 补丁的实现，式 5.8–5.14；本节末尾的局限与 ROME 预告）· 本篇为 clean-room 重写，例题与代码均为自编并已运行验证

## 一句话核心观点

**T-Patcher 的全部手艺只有一招：在最后一个 Transformer 层的全连接前馈层里，多塞进一对键值向量当补丁——键负责认出那道要改的题，值负责在认出时把输出拨向正确答案，原模型参数全部冻结、只训补丁。补丁的训练目标被拆成两组损失：准确性损失管该亮时亮、亮了改得对；局部性损失管不该亮时别亮、和无关输入拉开差距。它在表 5.2 里准确性、泛化性、可迁移性三高、局部性中，但不支持批量编辑，批量时内存需求高——它是一件单点精修工具，不是一条批量流水线。**

## 详细解读

### 1. 位置：为什么偏偏贴在最后一层的前馈层

上一篇（第 24 篇）登记过它的坐标：和 CALINET 一样，动最后一个 Transformer 层的全连接前馈模块。本节把理由讲透，核心是一个视角——把前馈层看成一座键值存储体。前馈层里，上投影矩阵的每一列是一个键向量，下投影矩阵中与每个激活分量对应的那一份权重就是一个值向量，再配上各自的偏置与中间的激活函数。键向量各自对应一种文本模式，可以是某个词组模式，也可以是某个语义主题；值向量各自关联着一种输出分布。某个 Token 的查询向量进来，先和每个键算关联程度得到激活值，再拿激活值对所有值向量加权求和，就是这一层的输出。式 5.6 把这件事写成两行：激活向量等于查询与上投影矩阵相乘、加偏置、过激活函数；输出等于激活向量与下投影矩阵相乘、加偏置。

顺着这个视角，编辑的做法几乎是自己跳出来的：想给模型塞进一条新事实，就往这座仓库里多放一对键值——新的键认出新的模式，新的值给出新的下文。这就是补丁。只放在最后一层也有讲究：补丁的作用是修改模型的输出，放在最后一层，改动直接作用于最终输出，不会再被后面的层加工、稀释或干扰。前馈层本身结构又简单，少量参数就能实现有效编辑。我的脚本把这座仓库做成三维的玩具版并逐项验过，为下面一节的补丁等式打底。

### 2. 形式：一个补丁就是一对键值加一个偏置，式 5.7

补丁的形式与仓库的原有单元完全同构：一个键向量、一个值向量、一个偏置项。加上补丁之后，式 5.7 的写法是把补丁键拼进上投影矩阵、把补丁值拼进下投影矩阵，激活向量随之多出一维补丁激活值。把式子展开，结论干净得惊人：带补丁的输出，恰好等于原输出加上补丁激活值与补丁值向量的乘积，多一分不多一分。我的脚本对目标查询与无关查询各算了一遍，等式残差为零；目标查询的补丁激活为 1.00，输出的第二维被补丁值整整推高 1.00；无关查询的补丁激活为 0.00，带补丁与不带补丁的输出逐位相同。

这条等式就是 T-Patcher 全部安全感的来源：补丁能造成的全部影响被锁死在一项乘积里，激活为零时它等于不存在。代价也同样写在这条等式里：一个补丁只带一对键值，只能管一个模式。教材在实现一节里把这笔账挑明：对给定的编辑问题，为每个需要编辑的 Token 都添加一个补丁。我的脚本把参数账算清：一个补丁的参数是键、值各一个向量加一个偏置，设向量维度为 d 就是 2d 加 1；以 d 等于 4096 的示意维度算，单个补丁 8,193 个参数，只占示意一层前馈参数的约 0.0061%，确实极小；但一个目标回答有 5 个待编辑 Token 就要 5 个补丁，参数随 Token 数线性累加。单个便宜、逐个累加——记住这条账，后面批量编辑的短板就是它长出来的。

### 3. 实现之一：准确性损失——先管亮，再管改，式 5.8–5.10

位置与形式定完，剩下的问题是怎么训。规矩先立好：冻结模型的原有参数，只训练新加的补丁参数。训练目标分两组，先看准确性这一组。教材把准确性拆成两个先后问题：第一，目标输入来了，补丁亮不亮；第二，亮了之后，输出改没改对。两个问题各配一项损失。激活损失管第一个问题，式 5.9 把它写成目标查询与补丁键的激活值取负指数：激活越大，损失越是指数级地小。我的脚本把这条曲线打了出来：激活为负 1 时损失是 2.7183，激活为 0 时是 1.0000，推到 4 时只剩 0.0183；再做一个只训补丁键与偏置的玩具梯度步，五步就把这项损失从 1.000 压到 0.221，补丁确实被推着学会在目标输入下亮起。编辑损失管第二个问题，就是最常规的交叉熵：拿补丁作用下的预测输出与该补丁对应的目标 Token 比一致性。脚本的两类玩具算例里，补丁把目标 Token 的 logit 推高之后，交叉熵从 1.313 降到 0.313。两项按式 5.8 合成准确性损失：一项激活损失，加上一项带权重的编辑损失。

这里必须如实登记一处教材的符号口径不一致，不许替它圆。式 5.8 印的是准确性损失等于激活损失加上 alpha 倍的编辑损失，也就是 alpha 是编辑损失的权重；可是紧随公式的正文又写 alpha 是激活损失的权重。公式与正文对不上。本篇的处理是照公式 5.8 读，并在审稿说明里登记这一处出入，引用时以公式为准。同类问题在总损失那一步还会再出现一次，一并登记在第 5 节。

### 4. 实现之二：局部性损失——别乱亮，还要拉开差距，式 5.11–5.13

只训准确性会训出一个见谁都亮的补丁：目标题改对了，无关题被它顺手拨乱，局部性就塌了。所以第二组损失专门管激活范围，叫记忆损失，分两项。先说数据从哪来：T-Patcher 会随机保留一些先前已经处理过的查询向量，攒成一个记忆数据集，里面的查询都与当前编辑目标无关，专门在训练时充当无关输入的样本分布。有了这批反例，两项损失分工：第一项管别乱亮——把每个无关查询对补丁的激活值与一个指定的激活阈值比，超过阈值就产生惩罚；第二项管拉开差距——要求目标查询的激活值显著高于所有无关查询的激活值，差距不够指定阈值就受罚。我的脚本用三条无关查询的玩具记忆集复算：只认目标方向的好补丁，两项损失分别是负 0.70 与负 3.20；主要认无关方向的坏补丁，两项分别是负 0.39 与负 1.09，好补丁两项都明显更低，断言通过。

复算时有一个细节值得单独点出来，因为它最容易被误当成 bug 去修：式 5.12 与式 5.13 按教材印出的形式，是把每条无关查询的差值直接取平均，式子里没有常见的取正部截断。结果就是补丁达标时这两项可以算出负值，上面好补丁的两个负数正是这样来的。这不是脚本写错了，是照原文复算的结果。本篇照原文登记、不擅自替教材补上截断；真去实现时要不要加截断，是实现者自己的设计决定，不能冒充教材原意。

### 5. 总损失与符号账：式 5.14，以及两处对不上的地方

两组损失合起来就是总损失，式 5.14：总损失等于准确性损失加上带权重的记忆损失，展开后是编辑损失、激活损失与两项记忆损失的加权和。设计意图到此完整：一个总目标同时盯住四件事——亮得起来、改得对、不乱亮、差距够大。这也是它在表 5.2 里能拿到准确性、泛化性、可迁移性三高的训练侧原因：泛化与迁移不是靠背下原题，而是靠激活机制认模式、靠值向量给分布。

但这一节的符号账必须单独结清，因为本节里同一个字母被用了两次。第一处已在第 3 节登记：alpha 在式 5.8 的公式里是编辑损失的权重，正文却说是激活损失的权重，而式 5.14 展开时又写成编辑损失加上 alpha 倍的激活损失，与式 5.8 的展开正好对调。第二处：beta 在式 5.12 里是激活阈值，到了式 5.14 里又被用作记忆损失项的权重，同一个字母两个身份。本篇的处置统一：每一处都照教材原文登记，引用某个公式时只认那个公式自身的定义，不拿一处的符号去套另一处，更不悄悄改符号把账做平。读教材的人最容易在这种地方被带偏——照着式 5.14 调权重时调到的到底是哪个 beta，必须回到原文逐式核对。这条教训比 T-Patcher 本身更耐用。

### 6. 局限与它在全章里的位置：单点精修，不是批量流水线

教材在本节末尾自己把短板写清了三条。第一，架构敏感：在 GPT-J 上准确性与泛化性较好，但有研究表明它在不同模型架构上的性能会波动。第二，批量短板：批量编辑时对内存的需求较高，可能限制它在资源受限环境下的应用——与表 5.2 里它不支持批量编辑的标记互相印证，结构原因就是第 2 节那笔逐 Token 累加的账。第三，局部性只是中档：表 5.2 里它的局部性是中，不是高；别乱亮的损失设计得再细，补丁毕竟是往最后一层加的一项乘积，无关输入的查询只要与补丁键沾边就会被拨动，中档是诚实的分数。

教材据此把话锋交给下一篇的主角：ROME 表现得更加稳定，把知识编辑做成一个带线性等式约束的最小二乘问题，在准确性、泛化性与局部性上都表现出色。两条路线的对照到下一篇就完整了：T-Patcher 是往仓库里加新货架，原参数不动、加法可控；ROME 是找到仓库里存着旧货的那一格，直接把那一格的货换掉。一个加、一个改，下一篇拆改的那一路。

## 我的思考/应用

- **给自家系统做单点纠错，补丁式是默认首选，批量重修是例外。** T-Patcher 的形态翻译成工程语言就是：原系统不动，外加一条只在命中特定条件时生效的修正规则，命中才改、不命中逐位无影响。我们维护讲稿、课程与库存时，单条事实纠错优先用这种形态：勘误规则单独登记、带触发条件、可随时摘掉；只有同类错误成批出现时，才值得动底座批量重修。（成本：每条纠错要多写触发条件与摘除方式；收益：纠错可回滚、不伤无关内容；证据 B，式 5.7 的等式结构与教材的实现口径原文，本篇脚本复算通过）
- **任何修正规则都要同时配两组验收：该触发的触发对，不该触发的别触发。** 准确性损失与局部性损失的分工值得直接搬进我们的质检：一条勘误规则上线前，既要用目标案例验它改得对，也要拿一批无关案例组成固定的反例集，验它不误伤。没有反例集的纠错，等于只训了准确性、没训局部性，表 5.2 里局部性只有中档就是提醒。（成本：每类规则维护一份反例集；收益：误伤在上线前暴露，而不是等读者发现；证据 B，式 5.11–5.13 的记忆数据集与两项损失口径原文）
- **按 Token 累加的账提醒我们：逐条便宜不等于整批便宜。** 单个补丁只占一层参数的万分之六量级，看起来几乎免费；但它的计价单位是每个待编辑 Token 一个补丁，批量时内存需求高正是这样累出来的。我们做任何逐条处理方案时，先把计价单位问清：是按篇、按段还是按句计价，再估整批总账，不要被单条的便宜麻痹。（成本：立项时多算一笔总量账；收益：避免方案做到一半被规模压垮；证据 B，教材逐 Token 加补丁的口径与本节末尾批量内存局限原文）
- **读公式先查符号有没有被复用，这是本篇最耐用的收获。** 本节短短九个公式里，alpha 的权重对象在公式与正文之间对不上、到总损失展开时又对调，beta 一会儿是阈值一会儿是权重。符号复用不会让方法失效，但会让照着实现的人调错参数。以后读任何带公式的材料，先列一张符号表：每个字母在哪一式是什么身份，列完再读推导。（成本：读公式慢一截；收益：实现时不把阈值当权重调；证据 A，本篇以 PyMuPDF 提取的教材原文逐式核对，式 5.8 与其后正文、式 5.12 与式 5.14 的口径均可复查）

## 视频脚本要点（动画短片用）

1. 开场钩子：模型最后一层里藏着一座仓库，货架上全是它记住的模式。这一篇不拆仓库，只往里多塞一个小格子——一个只认一道题、只管一个答案的格子。它叫补丁。
2. 仓库动画：一座货架墙缓缓展开，每个格子的门牌是一个键、格子里装的是一个值；一道问题化作一道光扫过货架，被认出的格子依次亮起，亮光的强弱决定各自的货被取走多少——这就是前馈层平常干活的样子。
3. 贴补丁动画：工人推来一个只有一个格子的小货架，贴在整面墙的最后一排，接线只接两根：一根管认题，一根管出货。目标题的光扫过，新格子亮起、把答案拨正；无关题的光扫过，新格子纹丝不动，整面墙的出货和没贴之前一模一样。
4. 两盏灯动画：补丁头上两盏灯，一盏写着该亮时亮、改得对，一盏写着不该亮时别亮；训练就是反复拿真题和一筐无关题轮流考它，第一盏灯越练越稳，第二盏灯靠那筐无关题一次次把乱亮的冲动压回去。
5. 结尾钩子：补丁是加法，加得再准也只管自己那一格。下一篇换一种狠活：不加格子，先查清旧货到底存在哪一格，再直接把那一格换掉——ROME 登场。
