# NLP 读书笔记（14）：Prompt 工程与上下文学习——不改一个参数，把模型用到极致

> 来源：中文 NLP 教材（浙江大学），《Foundations of LLMs》讲义第三章 3.1–3.2 节
> 覆盖：书页码 97–120（3.1 Prompt 工程简介、3.2 上下文学习）· 本篇为 clean-room 重写，代码为自写示例并已运行验证

## 一句话核心观点

第二章结束时模型已经训好了，参数冻结。第三章换了一个问题：**不动一个参数，只靠递给模型的那段文字，能把它的本事榨出多少？** 答案分两层。第一层是 Prompt 本身：它不是"一句话"，而是任务说明、示例与待答问题拼成的一段输入，进模型之前先被切成 token、再查表变成向量——同一句话在不同词表下切法不同、成本不同。第二层是上下文学习（In-Context Learning, ICL）：把几个"题目—答案"示例写进 Prompt，模型不更新任何权重，仅凭读这几道例题就在推理时"现学"了任务的做法；示例给零个、一个、几个，分别叫零样本、单样本、少样本。**这一章的立场是：Prompt 不是玄学许愿，而是一门有对象（token）、有变量（示例的选择、顺序、格式）、有度量（下游准确率）的工程。**

## 详细解读

### 1. Prompt 是什么：一段被精心设计的输入

教材先给定义：Prompt 是用户为引导模型完成特定任务而设计的输入文本。它和普通提问的区别在"设计"二字——里面通常不只有问题，还包含任务描述、背景信息、示例、输出格式约束等一切能帮助模型对齐意图的材料。用第 11 篇的话说，Decoder-only 模型本质上只会做一件事：续写。那么 Prompt 工程的全部手艺，就是把任务伪装成一段"最容易被正确续写"的文本：你希望它输出什么，就先在输入里把那种文本的形状摆出来。

为什么这件事值得单开一章？教材 3.1.4 总结了三重意义，我按自己的话复述。其一，**降低使用门槛**：传统做法里每个新任务都要收集数据、微调一个新模型；有了 Prompt，不会训练模型的人也能用自然语言把任务交代清楚——Text-to-SQL 这类任务可以直接用写好的 Prompt 加现成模型在基准上跑分。其二，**倒逼数据质量**：用 Prompt 反过来生成与筛选训练数据（教材提到 Alpaca、Evol-Instruct 一类工作），Prompt 成了数据流水线的工装。其三，**通向智能体**：复杂任务可以拆成多步 Prompt 串联，让模型在工具与环境之间周转，Prompt 是这条链上唯一的"程序"。三条合起来看：参数高效微调（第四章）解决"小改"，Prompt 工程解决"不改"，两者是同一枚硬币的两面。

### 2. Prompt 进模型之前：分词与向量化

一段 Prompt 在被模型"读懂"之前要过两关。第一关是分词（tokenization）：把字符串切成词表里登记过的 token 序列，再换成 token ID。主流切法教材点了三种：BPE 按合并频率从字符往上拼子词；WordPiece 选合并时按似然增益挑；BBPE（字节级 BPE）干脆以 256 个字节为底座，任何语言、任何生僻字都先拆成字节再合并，永不出现"词表里没有这个字"。第二关是向量化：每个 token ID 去嵌入矩阵里查一行，得到它的向量表示，后续所有计算都发生在这组向量上（第 04 篇讲过）。

分词这一步藏着两个工程上天天要付的账。**第一是词表大小与切分粒度的权衡**：教材给了一张各家词表对照表——从三万量级（早期 LLaMA）到十五万量级（Qwen 系列）都有。大词表切得粗、序列短，但嵌入矩阵大；小词表省参数，但同一句话切得更碎、序列更长。**第二是"生育率"（fertility）差异**：教材实测口径下，中文平均约 1.3 个汉字才摊到一个 token，英文约 0.7 个词一个 token——也就是说同样的信息量，中文 Prompt 消耗的 token 数与英文不是一回事。我的验证代码用玩具分词复现了这个量级感：一段英文按词切是十几个 token，一段等义中文按字数与 1.3 的比例折算也在同一量级，但只要换模型、换词表，数字就变。结论很实际：估算上下文够不够用、API 账单多贵，必须按目标模型自己的分词器算，不能按字数拍脑袋。

### 3. 上下文学习：把例题写进考卷

3.2 节的主角是上下文学习。定义拆开说：给模型一段 Prompt，里面包含若干个"输入—输出"示例（demonstrations）和一个只有输入的新问题；模型在**不做任何参数更新**的前提下，模仿示例的模式补出新问题的输出。注意它和训练的区别：训练是把知识焊进权重，要算梯度、要更新参数；ICL 的"学习"只发生在一次前向计算里，关掉这次对话，什么都没留下。教材用"大模型即服务"点出它的现实土壤：当模型只能通过 API 调用、权重碰不到时，ICL 几乎是唯一能让模型适配新任务的手段。

按示例数量分三档。**零样本（zero-shot）**：只给任务说明和新问题，模型全靠预训练里学过的东西硬答——指令写得越像它在预训练里见过的格式，答得越好。**单样本（one-shot）**：给一个示例，主要作用是把输出格式钉死：标签写"积极/消极"还是"正面/负面"，示例说一遍胜过说明写三遍。**少样本（few-shot）**：给几个到几十个示例，模型能从中归纳出任务的判定边界，效果通常随示例数上升，但边际递减、且占上下文。教材的情感分类例子正是这个结构：几条"小浣熊吃干脆面"句子的情感标注在前，新句子在后，模型续写出它的标签。我的验证代码把三档 Prompt 原样拼了出来：零样本 48 字符、单样本 81 字符、三示例 141 字符——示例每多一条，成本是线性的，收益却不是，这是后面选例要算的账。

### 4. 示例怎么选：ICL 的性能一半在选例上

教材 3.2.2–3.2.3 把影响因素摊开讲，我归纳成四条可操作纪律。

**代表性优先于数量。** 示例要覆盖任务的真实分布：分类任务每个类别都要有例，边界情形（既像 A 又像 B 的）比典型例子更有信息量。只给"一眼能分"的例子，模型学到的边界在新问题上不顶用。

**标签分布要平衡。** 示例里某一类占压倒多数，模型会产生先验偏斜，含糊样本一律往多数类倒。我的玩具模拟把这件事量化演示了一遍：同一句信号含糊的句子，示例标签比例一偏，预测立刻翻面——这不是模型笨，是它忠实地把示例当成了世界样本。

**顺序有近因效应。** 排在最后的示例对预测的影响权重更高（模型续写时离它最近）。实务推论有二：最重要的示例放最后；或者干脆多换几种顺序投票，别把结果押在一种排法上。

**格式必须全程一致。** 示例之间、示例与问题之间，分隔符、字段名、标签写法要一字不差地统一。模型靠模式续写，格式一乱，它先要花力气猜"这回按哪种格式"，任务本身反而被挤到边上。这一条零成本、纯纪律，是全部因素里性价比最高的一条。

此外教材也提醒：示例与新问题越相似（同领域、同句式），ICL 收益越大；示例本身的质量（标注是否正确）是天花板——写错一个标签，等于亲手教错一课。

### 5. 这一节与前后章的咬合

往回看：第 07 篇说能力随规模涌现，ICL 正是最典型的涌现能力之一——小模型给再多示例也学不会"看例题做题"，规模上来之后它自己长出来了。第 11 篇的少样本提示就是 ICL 在 GPT 家族身上的首秀。往后看：3.3 的思维链是 ICL 的一种特殊示例形态——示例里不光给答案，还给推理过程；3.4 的技巧篇会把本节的纪律细化成编写规范；第四章参数高效微调则是当 Prompt 榨干之后才需要动的那一步。顺序本身就是方法论：**先把不花钱的 Prompt 用尽，再考虑花钱动参数。**

## 代码验证（已运行）

自写脚本 `14-prompt-icl-verify.py`（仅标准库，固定示例，可复现），做了四件事：同一情感分类任务的零样本/单样本/少样本 Prompt 拼装与长度对照；中英文 fertility 的玩具估算；用带"标签先验+近因偏置"的玩具分类器模拟示例顺序与标签偏斜对预测的影响；示例标签分布统计。

```python
def build_prompt(examples, query):
    parts = [TASK]
    for text, label in examples:
        parts.append(f"句子：{text}\n情感：{label}")
    parts.append(f"句子：{query}\n情感：")
    return "\n".join(parts)
# zero-shot 48 字符 / one-shot 81 字符 / few-shot(3例) 141 字符
```

**实际运行输出**（节选，已验证）：

```
--- few-shot: 141 字符, 示例 3 条 ---
判断下面句子的情感为积极还是消极。
句子：小浣熊吃了烧烤味干脆面，脸上露出满意的笑容。
情感：积极
句子：小浣熊连续吃了20包烧烤味干脆面，撑得肚子疼。
情感：

=== 顺序与偏斜效应（玩具模拟）===
原始顺序(末条=积极): 对含糊句子的预测 = 消极
示例全为积极(偏斜): 对含糊句子的预测 = 积极

```

几点说明：玩具分类器不是真模型，它只演示"先验+近因"这两个被真实研究反复观测到的效应方向，数值不可外推到真实模型；fertility 用玩具分词只看量级，真实数字以各模型官方分词器为准（教材表格即一手口径）；Prompt 拼装部分是真实可用的字符串逻辑，换上真模型 API 即可直接跑。

## 我的思考/应用

- **我的日常 Prompt 模板要按本篇纪律返修一遍：格式钉死、示例平衡、关键示例放最后。** 我给各条生产线的指令本质上都是 few-shot Prompt——审稿、拆书、提炼大纲都靠示例定格式。按 3.2.3 的四条逐项自查：分隔符是否全程一致、分类类示例是否等量、最重要的示例是否在末位。（成本：一次性梳理约半小时；收益：各线输出格式漂移与分类偏斜下降，返工减少；证据 B，效应方向为教材与多篇研究共识，幅度因任务而异）
- **Token 预算按目标模型的分词器算，不按字数估。** 中文约 1.3 字/token 只是跨模型平均，换模型就变；长文档提炼喂料前先用对应分词器数一遍 token，再决定切分与摘要比例，避免中途截断丢尾。（成本：每次喂料多一条计数命令，近零；收益：杜绝"塞一半被截断还以为读完了"这类静默翻车；证据 A，fertility 数据为教材实测表）
- **先 Prompt、后微调的顺序写进选型纪律。** 新任务先用零样本试、再加示例、再上思维链，三档都试完仍不达标，才轮到考虑微调或换模型——这与第四章的预告正好接上：动参数是最后手段，不是第一反应。（成本：0，流程口径；收益：避免为能靠几条例题解决的问题付训练与部署成本；证据 B，教材章节编排与业界通行做法一致）
- **示例库要当资产维护，而不是每次现编。** 每条线沉淀一组验过标注的"金示例"（含边界情形），新任务从库里挑、按顺序规范拼，比每次临场编示例稳定得多；示例标注错一条，等于系统性教错，要按代码同等标准审。（成本：建库约 1 小时+日常维护数分钟；收益：跨会话输出一致性上升，与"状态文件"纪律同构；证据 C，我的工程经验判断）
- **给 Ezra 的一句话翻译：会写 Prompt 就是会给 AI 留例题。** 以后他直接指挥模型干活时，最有效的动作不是把要求说得更长，而是贴一条"照着这个样子来"的成品示例——格式、口径、详略全在示例里，比形容词堆叠可靠。（成本：0，沟通习惯；收益：他本人下指令的一次到位率上升；证据 B，ICL 机制的直接推论）
