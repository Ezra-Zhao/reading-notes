# NLP 读书笔记（17）：Prompt 应用——把技巧拼成系统

> 来源：中文 NLP 教材（浙江大学），《Foundations of LLMs》讲义第三章 3.5 节
> 覆盖：书页码 138–147（3.5 基于 Prompt 的应用：Agent、数据合成、Text-to-SQL、GPTs）· 本篇为 clean-room 重写，例题与代码均为自编并已运行验证

## 一句话核心观点

第 14–16 篇讲的都是单个 Prompt 怎么写，**3.5 讲的是把 Prompt 当成系统零件来拼装的四种用法：给模型配上配置、记忆、规划和行动，做成能自己干活的 Agent；让模型按 Self-Instruct 的流水线给自己造训练数据；把数据库结构塞进 Prompt，让模型把人话翻译成 SQL；再把一整段 Prompt 连同说明打包成一个人人可用的 GPTs。** 四种应用形态不同，内核是同一件事：模型本身不改，能力边界靠输入端的组织方式往外推——推到哪一步，取决于 Prompt 之外还给它配了什么：记忆、工具、数据回路，还是一套可分发的配置。

## 详细解读

### 1. 这一节的位置：从手艺到系统

3.4 收尾时说过，四组技巧是零件，3.5 是拼装。拼装的层次分四档：Agent 是把 Prompt 放进一个带记忆和工具的循环里，Prompt 从"一问一答"升级成"每一步的决策依据"；数据合成是把 Prompt 当成生产线，让模型批量生产能反过来训练模型的数据；Text-to-SQL 是把 Prompt 当成翻译器，输入端多塞了一样东西——数据库的表结构；GPTs 则干脆把 Prompt 本身做成产品，一段写好的指令配上说明和界面，就成了别人能直接用的定制模型。读这一节要抓住一条线：每往外走一档，Prompt 承担的角色就重一分，出错的代价也大一分，所以每一档都自带一套"防错机制"，这正是下面各节的看点。

### 2. Agent 之一：四个模块，Prompt 无处不在

教材给出的通用 Agent 架构由四个模块组成。**配置模块（Profile）**定义它是谁、干什么、按什么规矩干，落地方式就是一段角色与任务的 Prompt——第 16 篇讲的角色扮演，在这里成了开机配置。**记忆模块（Memory）**存两类东西：长期沉淀的知识与事实（教材例子里是动物的饮食习性这类背景知识），以及本轮任务中查到、用到的信息；它解决的是大模型"聊完就忘"的先天缺陷，存取同样靠 Prompt 把相关记忆捞出来拼进上下文。**规划模块（Planning）**把大任务拆成子任务序列，教材的例子是把"宠物不舒服怎么办"拆成先查习性、再看急救说明、再找附近医院、最后规划路线，拆解的方法论正是第 16 篇的分步引导与思维链。**行动模块（Action）**按子任务真正动手：调用搜索引擎、地图这类外部工具或 API，把结果拿回来。四模块转一圈：配置定身份，记忆供上下文，规划定步骤，行动出结果，结果再写回记忆，支撑下一轮规划。我的验证脚本把这四模块做成了一个最小可运行的闭环：仓库助理按规划逐个查库存与补货点，结果写回记忆，最后汇总出哪一箱要补货——麻雀虽小，循环是完整的。

### 3. Agent 之二：两个代表系统

教材举了两个例子说明这套架构能长多大。**Generative Agents**（生成式智能体）用 ChatGPT（原论文用 gpt-3.5-turbo）驱动一批虚拟角色在小镇里生活：每个角色有自己的记忆流、日常规划和对其他角色的反应，涌现出事先没有人编排的社会行为——它证明的是记忆加规划足够认真时，Agent 能撑起持续运行的世界，而不只是一次问答。**HuggingGPT** 则把 ChatGPT 放在总控位置：用户给一个复合任务，总控先规划，把图像、语音、文本等子任务分发给 Hugging Face 上已有的专用模型去执行，再汇总各家结果作答——它证明的是另一条路线：大模型不必样样自己会，当好调度员，调动一群专才，同样是 Agent。两条路线一个向内深挖（记忆与拟人），一个向外扩展（工具与生态），共同点是中枢都靠 Prompt 做规划与分发。

### 4. 数据合成之一：为什么让模型给自己造数据

这一节开篇先立了一条数据工程的老规矩：垃圾进、垃圾出。指令微调需要大量"指令—回答"数据，全靠人工标注又贵又慢。转机在 2023 年前后出现：研究界发现，可以反过来用大模型自己，按 Prompt 批量生成这类数据，再拿去微调模型——教材把这条路线的主要方法称为 Self-Instruct。它的赌注是：模型的生成能力已经足够当"出题人兼答题人"，缺的只是一套把生成管起来的流水线，让产量上得去、质量下不来。这也是整节与上一节的隐秘联系：Agent 是用 Prompt 调动外部工具，数据合成是用 Prompt 调动模型自己，生产资料就是模型本身。

### 5. 数据合成之二：Self-Instruct 的五步流水线

流水线从少量人工写的**种子任务**出发（原论文是 175 条），然后循环五步。**第一步，生成新指令**：每轮从任务池里抽 8 条指令作示例，拼成 Prompt 让模型续写出一条新指令，任务池就这样滚雪球；原论文给这 8 条定了配比：6 条人工种子、2 条此前已生成的任务——以种子为主锚住质量，再借已生成任务扩多样性，防的是雪球越滚质量越漂。**第二步，判断任务类型**：先让模型分清新指令是分类任务还是生成任务，因为两类的数据造法不同。**第三步，按类型生成数据**：分类任务反着来——先定分类标签，再按标签编出符合该标签的输入，避免先编输入再贴标签时两者对不上；生成任务则直接构造输入并写出回答。**第四步，过滤**：与任务池里已有指令太像的（原论文用 ROUGE-L 重叠度设门槛）、格式坏的、关键词违规的，一律丢弃。**第五步，合格的新指令回池**，进入下一轮抽样。我的验证脚本复刻了其中的过滤环节：一条只改了语气词的"新指令"与池中旧指令重叠度 0.93，被当场丢弃；一条真正的新任务重叠度 0.23，保留入池。流水线的灵魂不在"生成"，而在"过滤"——没有过滤这一步，雪球滚出来的只会是一堆近重复的废料。

### 6. Text-to-SQL 之一：把表结构写进 Prompt

Text-to-SQL 要解决的问题很实际：数据库只认 SQL，业务人员只会说人话。做法是把数据库的 Schema（有哪些表、每张表哪些字段）连同用户的自然语言问题一起写进 Prompt，让模型输出对应的 SQL 语句。教材的例子里给了 Owners、Dogs、Raccoons 三张表的结构，问题是某只宠物主人的名字，模型要自己完成三件事：看懂问题问的是谁的属性（表结构链接）、找出要跨哪两张表连接（Owners 与 Raccoons 按 owner_id 连接）、把过滤条件落在正确的字段上。这三件事没有一步是查表能查到的，全靠模型把 Schema 与问题对齐——所以 Schema 给得全不全、字段名清不清楚，直接决定 SQL 对不对，这正是第 16 篇"上下文丰富且清晰"在数据库场景里的翻版。我的验证脚本用 sqlite 真建了这两张表并执行模型式生成的 SQL，结果当场可验：查到了正确的那位主人。

### 7. Text-to-SQL 之二：C3 的三招防错

教材重点拆了一个有代表性的框架 C3（用 ChatGPT 做零样本 Text-to-SQL），它的价值不在"能生成"，而在三招防错。**第一招，清晰提示（Clear Prompting）**：版式清晰——用统一标记把指令、Schema、问题切开（第 16 篇排版规范的原样复用）；上下文清晰——Schema 只给与问题相关的表和字段，噪声表字段剔出去，免得模型选错表。**第二招，提示校准（Calibration with Hints）**：先把一批已知的常见偏误写成提示词喂给模型，比如某类统计写法容易多算、某些连接写法容易带出多余结果，让模型带着"别犯这些错"的清单再去生成——等于把历次踩坑攒成的检查表前置进 Prompt。**第三招，一致输出（Consistent Output）**：同一问题采样生成多条 SQL，全部真实执行，按执行结果分组投票，选结果票数最高的那条交付。这一步把第 15 篇的自一致性从"答案投票"升级成了"执行结果投票"：文字答案对不对只能靠猜，SQL 能跑、跑出的结果一不一致，是可以当场验的。我的脚本演示了这个投票：同一个问题的四条候选 SQL 写法各异，执行结果分出三组，两条不同写法跑出同一正确结果的那组以 2 票胜出。Text-to-SQL 因此成了四种应用里"可验证性"最强的一个——这也是它在企业里最先落地的底气。

### 8. GPTs：把一段 Prompt 做成产品

第四种应用最轻：OpenAI 的 GPTs 允许用户不写代码，只填名称、描述（Description）和指令（Instructions），再配上知识文件与可用工具，就发布一个定制版模型。教材点破了它的本质：**Description 是给人看的说明书，Instructions 就是这个定制模型的核心 Prompt**——所谓"定制"，绝大部分工作量就是把第 14–16 篇的技巧写进那段指令里：角色是谁、任务怎么拆、输出什么格式、遇到什么情况怎么处理。GPTs 的意义不在技术新意，而在分发方式：Prompt 从工程师手里的字符串，变成了带名字、带图标、能被搜索和分享的产品。随之而来的另一面教材也点到了：Prompt 本身成了资产，也就成了会被套取、被仿冒的对象，写进指令里的内部规矩和知识，从发布那一刻起就要按"可能被看见"来管理。我的验证脚本把 GPTs 配置按四件套思路做了体检：描述、明确动词、输出格式三项齐全的配置过检，三项全缺的空配置被逐项报出问题——和第 16 篇体检的是同一张清单，因为本来就是同一种东西。

### 9. 四种应用的共同账本

把四节并排看，能算出一笔共同账。**共性一：能力来自编排，不来自改参数。** Agent 的工具、Self-Instruct 的任务池、C3 的校准清单、GPTs 的指令，本质都是在模型外面加结构。**共性二：每种应用都配了自己的验货环节。** Agent 靠行动结果回写记忆再校验，数据合成靠过滤，Text-to-SQL 靠执行投票，GPTs 靠发布前的配置自查——没有验货环节的 Prompt 应用，就是把第 15 篇里"直答心算"的风险放大到系统尺度。**共性三：失败模式同源。** 四种应用翻车时，原因高度集中在前三篇讲过的老地方：上下文给错或给杂、任务没拆清、输出没法验。学 3.5 的正确姿势不是背四个名词，而是认出每个应用里藏着的 3.1–3.4 的零件，并检查它的验货环节在哪。

### 10. 与下一章的咬合

往回看：3.5 是第三章的收官——Prompt 的四要素、上下文学习、思维链、四组技巧，在这一节全部找到了系统级的落点。往后看：第四章转向微调与参数高效微调（PEFT），解决的是 Prompt 够不着的那部分问题：当任务要的是稳定的新能力而不是临场发挥，当上下文窗口塞不下要教的东西，就得动参数了。两章的分工正好划出一条工程分界线：能靠 Prompt 编排解决的，不动参数，成本低、迭代快；编排解决不了的，再进微调。下一篇进入第四章，先讲参数高效微调的全景：为什么只动一小部分参数，就能换来接近全量微调的效果。

## 代码验证（已运行）

自写脚本 `17-prompt-apps-verify.py`（仅标准库，固定数据，可复现），做了四件事：Agent 四模块的最小闭环（规划拆任务、行动调工具、结果回写记忆、汇总补货提醒）；Self-Instruct 的近重复过滤（词面重叠度门槛）与分类任务"先标签后输入"的顺序演示；Text-to-SQL 在真实 sqlite 小库上的生成与执行，外加按执行结果投票的一致性输出；GPTs 式配置的四件套体检。

```python
def max_overlap(new, pool):
    nb = bow(new)
    if not nb:
        return 0.0
    return max((len(nb & bow(old)) / len(nb) for old in pool), default=0.0)
```

## 我的思考/应用

- **我们自己的 Agent 排产，先查四模块齐不齐，再谈聪明不聪明。** 豆豆现在跑的各条生产线，本质都是 Agent：配置是各线的任务书，记忆是台账与日志，规划是 cron 的拆解，行动是上传与发布工具。哪条线出问题，先按四模块定位：是配置写糊了、记忆没回读、规划没拆步，还是行动没回执——比笼统怪"模型不行"准得多。（成本：0，排障顺序的纪律；收益：故障定位从感觉变成清单；证据 B，教材四模块架构的直接应用）
- **分发门禁就是 Agent 的验货环节，缺了它再能干也是裸奔。** 本篇四种应用每种都自带验货：过滤、执行投票、结果回写。我们立的"分发回读成功才放行下一批"与 C3 的执行投票是同一种思想：不看它说自己干完没，看可验证的结果。凡是新搭的自动化线，上线条件里必须写明它的验货动作是什么，写不出来就不许上线。（成本：每条线设计时多一道自问；收益：避免无回读的批量生产把错误放大成库存；证据 B，教材四种应用防错机制的共同推论）
- **合成数据可以用，但过滤门槛要先于产量定死。** Self-Instruct 给我们的现成用法是扩充各类模板与示例库（话术变体、标题变体、问答对），但入池规则必须先行：近重复丢弃、格式校验、人工抽检比例写死。没有过滤的合成，等于用模型的平均口味稀释自己的数据资产。（成本：过滤脚本一次性开发，约半天；收益：示例库规模可放大且不注水；证据 B，教材 Self-Instruct 五步中过滤环节的直接推论，脚本已实测演示）
- **凡是能落到"可执行验证"的任务，优先设计成 Text-to-SQL 式闭环。** 查账、查库存、查台账这类任务，与其让模型直接报数字，不如让它生成查询、真执行、拿结果作答，再加多候选执行投票。数字对不对从"信不信它"变成"跑没跑通"，这是我们所有数据类汇报该走的路。（成本：查询类任务要多一层生成与执行脚手架；收益：数字类错误从静默变显形，且可复核到查询本身；证据 B，教材 C3 一致输出机制的直接应用，脚本已实测演示）
- **平票与全错，是执行投票的两个盲区，要提前留后手。** 投票只能选出"多数一致"的结果；候选全错时它会自信地选一个错的，平票时无所适从。工程上的补法：候选必须来自不同的生成路径（不同提示或不同温度），平票时追加一轮带校准提示的再生成，而不是随便挑一条。（成本：0 到少量额外调用；收益：堵住投票机制最危险的两种失效；证据 C，我的工程经验判断，教材未展开）
- **GPTs 式打包值得抄：把成熟 Prompt 做成带说明书的成品。** 我们各条线的成熟提示（审稿、拆书、战报）现在散在任务书里，照 GPTs 的形态打包——名称、一句描述、完整指令、适用边界——内部复用和交接都会快得多。同时按教材的提醒执行：打包即按"可能被看见"管理，敏感口径不写进指令正文。（成本：每条线约一小时整理；收益：提示资产从散稿变成可交接的产品件；证据 C，我的工程判断，与教材 GPTs 一节的机制一致）

4. SQL 投票动画：同一个问题变出四张写着不同查询的票，四张票同时塞进数据库形状的投票箱，箱子吐出三堆结果，两堆一样多、一堆只有一张，镜头推近那堆多数结果被盖上交付章——"文字答案对不对靠猜，SQL 对不对，跑一遍就知道。"
5. 结尾钩子："四种应用有个共同点：全都没动模型一个参数。可有些活，编排再精巧也干不了——下一篇进第四章，开始动参数：只动一小撮，效果却接近全量微调的参数高效微调。"
